# Saved mobile CV editing contract

The tailoring review remains read-only. On Changes (Step 2 of 2), Continue to CV first checks the latest server preview and then sends `expected_preview_id` to `POST /api/v1/mobile/tailor/{tailoring_id}/confirm`. Railway atomically rejects a changed preview. A successful acknowledgement opens the saved tailored CV PDF preview; older bodyless confirmation clients remain compatible.

All editor operations require the existing Supabase bearer session and ownership of the tailoring record and its saved engine resume. They never modify the uploaded original. The unauthenticated desktop routes stay blocked in mobile deployments.

## Canonical document and autosave

- `GET /api/v1/mobile/tailored-cvs/{id}/editor` returns `tailoring_id`, integer `revision`, `updated_at`, structured `resume`, job context, `confirmed_skills`, and optional analysis. This is current engine content, not the original confirmation snapshot.
- `PATCH` on the same route accepts `expected_revision`, a secure UUID `mutation_id`, `resume`, and `confirmed_skills`. The existing schema is validated while raw fields and metadata are preserved. User edits do not run AI rewriting or overwrite their original CV.
- Content, immutable revisions, and mutation receipts are saved atomically in the existing private mobile engine database on Railway’s persistent volume. A repeated mutation returns its own acknowledgement; different content cannot reuse the same mutation ID. Stale versions return 409. Invalid documents return 422 without replacing the last valid revision.
- Frontend recovery drafts include the canonical base revision, latest edits, confirmations, and any pending mutation. They are scoped by account and document, written before transport, and retained after ambiguous failures. Session generations fence late writes. Conflicts require an explicit choice; exports wait for the latest saved acknowledgement.
- `GET /api/v1/mobile/tailored-cvs?status=ready&limit=30&offset=0` lists owned saved documents and canonical save timestamps for reopening.

## Job Match

`GET/POST /api/v1/mobile/tailored-cvs/{id}/ats-score` retrieves or recalculates analysis; POST accepts `expected_revision`. Results include current/stale/unavailable status, analyzed revision, calculation time, job hash, scoring version, score breakdown, complete matched/missing evidence, and required/preferred skills. Recalculation is deterministic from cached job extraction, without AI generation. Missing extraction remains unavailable rather than a fabricated score. Rendering and scoring normalize visible supported content consistently.

User-confirmed skills can be saved freely alongside their resume edits. Confirmation means the user personally attested possession; it does not fabricate work history, certificates, or achievements.

### Mobile editor layout and evidence limits

CV Editor opens on Edit CV → Resume Content. The main Edit CV / Job Match tabs are visually stronger than their secondary tabs. Edit CV contains Resume Content / Design & Layout; Job Match contains Overview / Keyword Highlights and initially selects Overview. Selections are remembered separately for each main tab while the editor is open, and reset for another account/document. Tab switches dismiss the keyboard and scroll the content area to its start without replacing the save session. The Job Match component stays mounted across main-tab switches so its disclosure state and Your Resume / Job Description selection survive. Resume Content honors existing sectionMeta displayName/order and keeps Personal Information as the header. For legacy metadata-free documents it uses Personal Information, Summary, Experience, Education, Skills, then remaining sections; missing metadata is completed before content saves or export so the engine receives the same default names/order. The engine’s additional object stays one Skills section, with its existing sublists. Resume Content begins directly with full tappable section rows and no intro block. Rows show a title (up to two lines for custom sections), one-line preview or entry count, a chevron and an adjacent 44-point ellipsis target that cannot shrink; the full title/preview area opens the editor. Add Custom Section is the last row. Skills subtitles identify Languages when any nonblank language is present. Empty sections retain type-specific hints. SectionEditor sheets preserve raw schema and autosave. Section actions use the same trailing ellipsis in the list and editor header area. Custom editors show a visible Section actions label beside it on a separate row, leaving the title and Done button their own space. A bottom menu groups Rename, Move Up/Down, Duplicate where supported, and a final red Delete Section for custom content. Rename updates only displayName; moving persists section order. The menu disables boundary moves and omits unsupported whole-section actions. Delete first names the section in confirmation; only confirmation removes its customSections entry and every matching bare/prefixed sectionMeta record. Built-ins cannot enter that delete path. The local removal uses the existing serialized PATCH/recovery flow, then immediately flushes; pending older saves cannot replace the newer deletion draft. Closing a deleted section returns to the mounted list. Preview still waits for acknowledgement and uses the same frozen PDF artifact for display and download. Individual item removal stays inside the editor and uses Remove item. iOS menu actions wait for native modal dismissal before changing sheets or closing the editor. Add Custom Section stores content under a unique customSections key with sectionType text/itemList/stringList and complete sectionMeta, then opens the editor after iOS creation-sheet dismissal. Individual entry/bullet menus duplicate immediately below the source, deep-clone unknown fields and formatting, generate independent existing IDs, and duplicate/reorder/remove descriptionStyles alongside their bullets. The list stays mounted while a sheet is open; its offset is captured on opening and restored on closing, which also flushes edits through the existing serialized save. Opening/closing sheets does not trigger the tab-switch scroll reset. Section fields use EditorTextField: an in-flow, accessibility-hidden text mirror sets intrinsic height from the full current value and a zero-width final character preserves a trailing empty line. The overlaid multiline Input shares its font, line height and padding, has no numberOfLines limit or internal iOS scrolling, and stays mounted as text changes. Summary has a larger minimum size; other fields fit short values and grow naturally. Saved text, typing, paste, width/font changes and parent card layout use the same sizing path, without waiting for focus or a content-size event. Experience, Project and custom-item description bullets use the shared rich editing document in a native WebView or sandboxed web iframe. Its toolbar appears for the active field, toggles Bold/Italic/Underline on the selection, and opens an inline link sheet with Display Text/URL plus edit/remove. A DOM selection is retained while editing a link; unchanged linked text keeps its marks. User text never enters executable HTML: initial values are JSON-escaped and DOM-parsed through the print vocabulary; scripts, styling and unsafe link protocols are excluded. The saved value remains strong/em/u/a HTML, not editor-specific JSON. Full DOM height and native caret coordinates keep wrapped text visible; parent acknowledgements do not replace the active DOM/selection. Plain fields retain their full raw string and numeric conversion. The iOS section ScrollView adjusts keyboard insets and focused-selection visibility; its KeyboardAvoidingView is disabled on iOS to avoid double adjustment. Android retains its existing keyboard avoidance. Done stays in the header outside the scrolling body. Recommendations switch to Resume Content and open the matching section editor. The Design & Layout secondary tab links to the actual A4/Letter controls in Resume Preview after the existing save acknowledgement; it no longer opens a separate sheet.

Job Match shows `score.overall_score` out of 100, `matched_count` of `total_keywords`, and `score.sub_scores.keyword_match` as the percentage. Display server numbers without further rounding or recomputing the percentage. The inspected scorer returns one decimal of precision. Current means saved content, `status: current`, and matching `analysis.revision`; dirty content or a different revision makes displayed scores previous results. Update Match retains serialized save-before-analysis. Overview disclosures follow ATS Score Breakdown, Missing Keywords, Recommendations, About Job Match & Tips. Keyword Highlights is a separate secondary tab, not an Overview disclosure. PDF readability stays in Resume Preview.

The current `GET/POST /api/v1/mobile/tailored-cvs/{id}/ats-score` contract returns keyword lists, counts, scores, `revision`, `job_hash`, `scoring_version`, and `calculated_at`, but no text ranges or insertion provenance. `confirmed_skills` records attestation only: it does not prove where a term was inserted or that it still exists in the saved revision. Keyword Highlights therefore switches between a current engine-matched keyword list and the stored job description. Its legend reserves yellow for matches and blue for user-added placements, but no keyword is colored blue and no inline text location is inferred. Stale results cannot populate the current verified list. Highlights never modify PDF export.

For inline highlighting the backend must add explicit revision-bound evidence. Proposed fields: `highlight_evidence.revision`, `highlight_evidence.resume_content_hash`, `highlight_evidence.job_hash`, and `highlight_evidence.offset_encoding` (`utf16`); `highlight_evidence.resume_locations[]` with `{keyword, resume_path, start_offset, end_offset, exact_text, origin, added_revision, verified_revision, still_present}`; and `highlight_evidence.job_locations[]` with `{keyword, start_offset, end_offset, exact_text}`. Paths must identify the canonical visible plain-text field, offsets must address that exact text, and provenance must distinguish an original engine match from a user edit/confirmed insertion. Blue requires server-verified user-added provenance, matching current saved revision/content, and an exact placement still present at that path/range. The server must revalidate or remove evidence after every edit. These are required additions, not fields the current app assumes exist.

The mobile PDF endpoint currently accepts only immutable `revision` and `page_size=A4|LETTER`, and `_render_snapshot` fixes `swiss-single` with default font size, spacing and margins. Templates/font size/line spacing/margin controls require validated, capability-advertised layout settings accepted by the mobile API, persisted with immutable revisions, returned by editor GET/PATCH, and consumed identically by PDF and parse-check rendering. Unknown raw document fields are not proof of rendering support. These controls remain hidden until that contract exists.


### Mobile design references

The compact text rows and short, grouped menu labels follow [Apple lists and tables](https://developer.apple.com/design/human-interface-guidelines/lists-and-tables), [Menus](https://developer.apple.com/design/human-interface-guidelines/menus), and [Context menus](https://developer.apple.com/design/human-interface-guidelines/context-menus), including separating destructive commands at the end. Mobile document patterns were reviewed in [Pages for iPhone](https://support.apple.com/guide/pages-iphone/tan239d80198/ios), [Word mobile view](https://support.microsoft.com/en-us/word/use-word-views-to-read-or-edit-your-document), and [Google Docs for iPhone](https://support.google.com/docs/answer/49114?co=GENIE.Platform%3DiOS&hl=en). The app keeps content editing distinct from section management and PDF layout, with secondary actions reachable from the same visible ellipsis and a bottom menu.

## Actual PDF preview and export

`GET /api/v1/mobile/tailored-cvs/{id}/pdf?revision=N&page_size=A4|LETTER` exports the identified immutable revision using the existing single-column Resume-Matcher print pipeline. Responses are authenticated, private/no-store PDFs with `X-Resume-Revision`, `X-PDF-Page-Count`, and `Content-Disposition` exposed to allowed browser origins. Missing layout metadata is completed without dropping populated supported/custom sections; explicit visibility flags remain respected.

The app validates the PDF response and displays/downloads the same artifact. The preview is the first destination from Tailor’s Open saved CV, Library’s Open cards, and Changes after it confirms the saved copy. Existing-CV entry points push the preview so Back returns to the originating screen. New confirmation replaces the review with the preview and its library-return marker, so Back opens Tailored CVs. Unsaved Tailor results still open Continue review. Its header shows the resume title and measured page count, an A4/Letter selector, and Edit Resume; Download PDF remains the bottom primary action. Each screen focus reads the latest saved document and pins the new artifact to that revision and selected paper size. An optional revision URL parameter is a minimum expected save, not a reason to retain an older artifact after editing. Edit Resume opens the existing editor with a preview-return marker. The editor waits for its existing serialized save before returning, retains the selected paper size, and stays open with recovery actions on save failure. Blur aborts preview reads and disposes the previous artifact; download remains disabled until the refreshed artifact is ready. iOS uses a cached file, WebView, and the native share sheet; web uses a Blob iframe/download. `POST /api/v1/mobile/tailored-cvs/{id}/parse-check` accepts `expected_revision` and `page_size` and checks a render of that same frozen document/settings. Readability checks are advisory and distinct from job match.

The inspected swiss-single renderer uses SafeHtml for Experience, Project and custom-item description arrays. Summary, Education descriptions, custom Text Block text and Skill List strings use plain React text; their formatting toolbars stay hidden. Rich formatting in those fields requires renderer support for sanitized HTML. The editor normalizes browser block/break elements to text newlines so PDF sanitization cannot concatenate adjacent words. The engine’s strict rich-text sanitizer strips explicit br tags and its current inline HTML uses normal whitespace; preserving authored hard line breaks in PDF needs renderer/sanitizer support. Existing supported marks and link annotations are transported in the same frozen revision used for both preview and download. Native text selection, keyboard behavior and Save to Files need device/simulator validation; source inspection and session tests do not establish live PDF fidelity.

Arbitrary unknown raw fields survive editing/storage; the existing print templates render the supported resume schema and `customSections`. Native PDF display and Save to Files must be checked on an iPhone simulator or published build.

### Backend pagination ownership and required behavior

Pagination is baked into the PDF returned by `https://resume-matcher-production-0ffd.up.railway.app/api/v1/mobile/tailored-cvs/{id}/pdf?revision=N&page_size=A4|LETTER`. The Expo viewer and download share that artifact; changing their layout cannot change its page breaks.

The Railway source at `246a6da3731e25f34feb865f008af0ca56d7e877` traces through `apps/backend/app/routers/mobile_editor.py` (`_render_snapshot`) → `/print/resumes/draft` → `apps/frontend/components/resume/resume-single-column.tsx` → Chromium PDF rendering in `apps/backend/app/pdf.py`. The export selects `swiss-single` and the requested paper size, with CV mode enabled.

The restrictive keep rules are in `apps/frontend/app/(default)/css/globals.css`: `[data-resume-item] { break-inside: avoid; }` keeps an entire role together. `apps/frontend/components/resume/page-break-attrs.ts` only marks entries with at least four bullets as splittable. Split entries still keep the first two bullets and last two bullets together. Section-heading keep rules carry the Experience heading with that larger group when it cannot fit; there is no explicit forced new page for Experience.

Required backend change: scope a flowing-entry policy to Experience in the mobile `swiss-single` print path. Allow roles to split between bullets regardless of bullet count. Keep the Experience heading, the first role's heading/company/date details, and its first bullet together; keep each later role's details with its first bullet. Remove the two-bullet leading/trailing grouping for these roles, preserve individual bullets where they fit on a page, and allow an oversized bullet to continue without clipping. Keep section containers splittable so Skills follows the preceding content naturally. Do not remove CV content, reduce readable font sizes, or impose a page count. If the desktop builder shares the changed policy, update its separate `components/preview/page-breaks.ts` keep zones to match; the Expo preview itself has no pagination algorithm.

Acceptance requires real renders of the same saved revision in both A4 and Letter: one case where the heading/role/first bullet fits below Summary but the complete role does not, and one where that leading group cannot fit. Check the actual preview and downloaded artifact, preserved text/order, page dimensions, readable type, natural continuation of bullets and Skills, and absence of clipping or duplicate content. These PDF checks remain outstanding until the separate backend template is changed and deployed; source inspection alone does not verify corrected pagination.
