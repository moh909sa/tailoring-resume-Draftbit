# About this app

This file describes this app's stack, structure, and conventions. **Keep it updated and short**: when the app gains a backend, new conventions, or significant structure, edit this file (and the README) in place so future sessions inherit that knowledge. This file is loaded into every session, so it describes the current state only. Never add dated or per-task entries, change logs, or test results, even if earlier ones exist. Put notable decisions in `docs/HISTORY.md` as one line each, and keep this file under about 200 lines.

## Stack

- Expo cross-platform app (iOS / Android / Web), TypeScript (strict), Expo Router (file-based routing under `app/`)
- NativeWind (Tailwind for RN) for styling
- Yarn Berry (v4.x) — check `.yarnrc.yml` for the linker; with Plug'n'Play there is no traditional `node_modules`. Patching dependencies is a last resort; use `yarn patch`, never hand-edit.
- React Query available for server state when a backend is wired
- Path aliases are defined in `tsconfig.json` `paths` — use them instead of long relative imports.

## Theming

Keep colors and typography centralized in the app's existing theme setup (Tailwind config, theme files, or CSS variables) and use them through NativeWind classes — never hardcode per screen. When changing colors/typography, update the central definitions. Support both light and dark with readable contrast if the app supports both.

## Conventions

- **Reuse first:** use the app's existing component, icon, and styling libraries and patterns before adding new ones. Check `package.json` and existing components before introducing a dependency.
- **Icons:** use the app's existing icon approach. If icons need NativeWind classes, make sure they go through a wrapper or interop that applies them.
- **Navigation:** set an explicit human-friendly `title` for every screen header — never let route names like `(tabs)` or `products/[id]` appear in the UI. Keep `app/index.tsx` for redirects, not feature UI; use `_layout.tsx` files for stacks/tabs.
- **NativeWind state changes:** initialize CSS-variable styles on the first render of reused native elements. Editor tabs always use a themed background in both states; every PDF loading/error/document state does too. Adding variable-bearing classes only after a state change can trigger NativeWind v4 provider upgrades and a misleading React Navigation context error. Expo Router owns the navigation container.
- **API routes:** server-only logic can live in Expo Router API routes (`+api.ts` files under `app/`). They require `web.output: "server"` in the app config and run in the preview; secrets they read use unprefixed environment variables, never `EXPO_PUBLIC_`.
- **Fonts:** load through the `expo-font` config plugin (declared in the app config) or `useFonts` in the root layout — follow whichever the app already uses.
- **Screens:** wrap in SafeAreaView (react-native-safe-area-context) and handle scrolling/gestures correctly. Keep bottom tab bars compact — pad content inside screens, not via `tabBarStyle`.
- **Components:** keep components small and focused, follow the app's existing folder structure, and reuse before creating.
- **Performance:** `FlatList`/`SectionList` for long lists — never `ScrollView` + `.map()` for large collections.

## Draftbit starter structure (if present)

Apps created from the Draftbit starter ship with the pieces below. Follow them where they exist; don't add them to apps that don't have them.

- **Theming:** `theming/ThemeProvider.tsx` injects theme objects (colors + typography) as CSS variables via NativeWind's `vars()`; typography is flattened (`h1.fontSize` → `--h1-fontSize`). Theme shape in `theming/Theme.ts`, concrete themes in `theming/themes/light.ts` and `dark.ts`, mapped to classes (`text-foreground`, `bg-background`, `text-h1`, `border-border`, …) in `tailwind.config.js`. `lib/useColorScheme.tsx` syncs the system preference. Use `useTheme()` only for raw values; change colors/typography in the theme files.
- **Components:** React Native Reusables (shadcn-style, `@rn-primitives/*`) in `components/ui/`, layout pieces in `components/layout/`, `cn` helper in `lib/utils.ts`. Build higher-level components on these primitives. Without `components/ui/` and `@rn-primitives/*` in `package.json`, compose React Native primitives with NativeWind instead and don't pull `@rn-primitives/*` in unless asked.
- **Icons:** `lib/icons/LucideIcon` wraps Lucide so NativeWind classes apply — `<LucideIcon name="Home" className="h-6 w-6 text-foreground" />`. Don't import from `lucide-react-native` directly, and validate `name` against the wrapper's registry.
- **Portals:** web uses `WebPortalContext`, native uses `PortalHost` from `@rn-primitives/portal`, both set up in `app/_layout.tsx`; the `components/ui/` primitives rely on them.
- **Alias:** `~/*` maps to the project root, e.g. `import { useTheme } from '~/theming/ThemeProvider';`.

## Current state

- `app/index.tsx` redirects to Home under `app/(tabs)/`. Bottom tabs are Home, Tailor, and Library. Library has My CVs and Tailored CVs screens with a shared section switcher; Home cards link directly to each screen. The legacy `app/my-cv.tsx` URL redirects to My CVs.
- `lib/supabase.ts` connects to existing project `suvcisvnbwplbemuxspu` with a publishable key only. `lib/auth/AuthProvider.tsx` restores sessions and manages native foreground token refresh. Native sessions persist through AsyncStorage; web sessions use Supabase's browser storage.
- My CVs reuses the existing email/password sign-in and account creation form in an account sheet. Existing Supabase settings require email confirmation.
- `lib/cv/api.ts` uses authenticated Railway mobile endpoints: multipart `POST /api/v1/mobile/resumes/upload`, `GET /api/v1/mobile/resumes`, and `DELETE /api/v1/mobile/resumes/{id}`. Tokens come from the current Supabase session. No direct Storage access or database writes.
- `lib/cv/file.native.ts` builds multipart files from native URIs; `file.web.ts` uses browser File objects. Expo DocumentPicker accepts PDF/DOCX, with client validation of the 4 MiB limit.
- `lib/cv/useMyCv.ts` refreshes on screen focus and after successful and failed upload requests, polls pending processing, and retains confirmed originals if refresh fails. Failed and recovery-required files stay visible and offer an explicit Retry processing action that reuses the retained original. Every My CVs card has a delete menu with confirmation, regardless of processing status; HTTP 204 triggers list refresh and confirmed deletions stay removed if refresh fails.
- Tailor CV uses Ready originals and pasted job descriptions (50–12,000 characters). `POST /api/v1/mobile/tailor/jobs` queues durable background work with `resume_id`, `job_description`, and a secure Expo Crypto UUIDv4 `progress_id`; existing Supabase bearer auth and server defaults apply. The preparation form accepts pasted text only, saves CV selection and exact job text in separate account-scoped device storage, and reopens an existing review or saved CV for identical inputs instead of submitting another job.
- `lib/tailoring/TailoringProvider.tsx` retains owner-scoped review state and clears/aborts client reads on account changes. The existing review cache keeps only draft/saved references, form inputs, step, selections, and pending review navigation; resume contents reload from Railway. `lib/tailoring/jobs.ts` persists the job UUID and inputs in a separate owner-scoped AsyncStorage record **before** submitting, then saves the backend’s canonical ID. The server worker is independent of client AbortControllers.
- Durable jobs support queued/running/succeeded/failed/interrupted. Foreground recovery checks the saved ID and authenticated `GET /api/v1/mobile/tailor/jobs/recent`; active jobs poll real progress every 1.75 seconds without overlapping GETs. Backgrounding pauses reads; foreground/relaunch resumes the same job. `GET /api/v1/mobile/tailor/jobs/{progress_id}/result` retrieves completed previews without AI, and root navigation opens the existing review automatically. A delivered-job marker prevents reopening older jobs.
- Recovery and network retries use GETs only. An ambiguous submission keeps its saved ID; only an explicit “Retry same job” can resend that idempotent request. Explicit Retry after a server-reported failed/interrupted job creates a fresh UUID. Definitive submission rejections retain their error and inputs without pretending a job was accepted; corrected inputs can be submitted explicitly. Client disposal never deletes the recoverable job record. Processing retains the purple animation, seven-stage layout, and wall-clock timer based on persisted/server start time; only real completed steps earn checks.
- Success opens the three-step review: Optimize Keywords, Review Changes, Confirm & Save. Review data comes from the backend `review` object. Supported keywords send `attested:false`; absent skills require an explicit “I have this” choice and `attested:true`. Continue to Changes is disabled while keywords are pending or a review request is active; users must apply or deselect the same pending selections shown by Apply Keywords. Successful application stays on Keywords; failed pending selections remain retryable. Keywords omits the placement accordion; confirmed placements remain in Where your keywords went on Changes. Keyword application uses the latest `preview.preview_id` and replaces the full review; scores, history, placements, counts, comparisons, and warnings are never simulated. Review and saved references survive sign-out while remaining scoped to their owner. The preparation form reopens the last matching saved result across relaunches.
- Changes combines current server-confirmed keyword locations per keyword. Description cards have no role/company headings, show the entire original bullet red and struck through, and use normal updated text with blue only for newly added keywords confirmed on the matching placement path. Underlines and generic description diff highlights are absent; Summary comparisons use full red Before strike-through and plain After text with only newly added, placement-confirmed keywords in blue. The neutral keyword card keeps the latest score pair and positive-delta badge visible, falling back to the current score alone; its accessible counted disclosure starts collapsed on entry to Changes, with foreground keyword rows and stacked neutral destination badges. Full comparisons and accuracy warnings remain visible. Only the skill-attestation note uses a yellow warning card; other review notes and accuracy reminders use neutral text without warning icons, retaining all recovery actions. Changes omits the Engine feedback accordion while retaining complete engine reports in underlying preview data for future editor use; save checks remain enforced.
- `POST /api/v1/mobile/tailor/{id}/keywords` sends `expected_preview_id` and selected keywords. Conflicts and ambiguous failures reload the server draft without retrying mutations. Expired drafts require explicit regeneration. Confirmation first checks the latest review, requires re-review if its preview ID changed, then calls `POST /api/v1/mobile/tailor/{id}/confirm` with `expected_preview_id` only after “Confirm & Save.” Acknowledgement opens the saved CV Editor. Tailored CVs lists owned ready documents with pagination and reopens the same editor.
- Saved CVs use authenticated `GET/PATCH /api/v1/mobile/tailored-cvs/{id}/editor`. Railway owns canonical content, immutable revisions, and mutation receipts; saves require `expected_revision` and `mutation_id`. User-authored edits and confirmed skills never overwrite the original CV. `lib/editor/session.ts` serializes autosaves, persists account/document-scoped recovery drafts before requests, retains ambiguous mutations for idempotent replay, and requires explicit conflict resolution.
- `app/cv-editor/` provides Edit CV / Job Match and actual PDF preview. Routes validate the saved tailoring UUID and optional positive PDF revision; parameter-free Draftbit previews require Routes input. Invalid links return to Library, and authentication/missing-CV errors preserve local recovery edits without treating them as offline saves. Job Match uses revision-aware deterministic backend scores, complete keyword evidence, and explicit confirmations for engine-identified required/preferred skills; other job keywords remain wording suggestions. Previously confirmed skills can be restored if missing from a later version. PDF export pins a saved revision and uses the existing single-column template with A4/Letter. iOS previews cached PDF files with WebView and shares via Expo Sharing; web previews/downloads the same Blob. Optional PDF readability checks use the frozen revision and paper size. PDF transport requires the exposed revision header to match the saved revision; late save acknowledgements cannot reopen preview after leaving the editor. Native PDF/share behavior requires native validation. See `docs/TAILORING_EDIT_CONTRACT.md`.
- `components/layout/` provides iPhone-first safe-area shells and headers; `components/library/` provides Library section navigation. Shared theme and icon wrappers cover all screens.
- Public configuration: `EXPO_PUBLIC_SUPABASE_URL`, `EXPO_PUBLIC_SUPABASE_PUBLISHABLE_KEY`, `EXPO_PUBLIC_RESUME_API_URL`. Never put server secrets in these variables.
- Railway's `CORS_ORIGINS` must allow the exact web preview/published origins for browser uploads; native iOS does not require CORS.
